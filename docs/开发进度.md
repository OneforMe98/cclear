## 步骤 3：流式输出，打字机效果（Phase 2b）✅ 已完成

**目标**：回答从"等全部生成完再出现"变成"边生成边逐字显示"。

**改动内容**：

- `backend/app/main.py`：
  - `/api/chat` 改为返回 SSE 流（`StreamingResponse` + `media_type="text/event-stream"`）
  - 新增 `stream_reply()`：用 `llm.astream()` 异步逐段读取模型输出
  - 新增 `chunk_text()`：兼容 LangChain 片段内容是字符串或内容块列表的情况
  - 约定事件格式：`data: {"delta": "文本"}`（正常片段）/ `data: {"error": "原因"}`（中途出错）/ `data: [DONE]`（结束）
- `frontend/src/api.ts`：
  - `sendMessage` 改为 `streamMessage`：用 `res.body.getReader()` 读流，按空行切分 SSE 事件，逐段回调
- `frontend/src/App.tsx`：
  - 发送时先放一条空的助手消息占位，收到的每一段直接追加进去（边收边渲染）
  - 首段到达前显示"打字中"动画；中途出错在气泡里追加错误说明
- 无新增、无删除文件

**学到的概念**：

- SSE（Server-Sent Events）：服务器向浏览器单向推送文本流的协议，格式就是 `data: xxx` + 空行
- 流式 vs 非流式：响应头一旦发出状态码就固定了（所以流中途出错只能靠事件通知，不能改状态码）
- 异步生成器（`async for` / `yield`）：一边产生数据一边发送
- 前端 `ReadableStream` + `TextDecoder`：浏览器侧如何消费"还没结束的"响应

**验收结果**：✅ 已完成

- 直连后端：HTTP 200，`text/event-stream`，共收到约 30 个网络分块，首块约 0.7 秒到达，正常收到 `[DONE]`
- 通过 Vite 代理：同样流式正常（约 27 个分块）
- 前端 `npm run build` 类型检查通过

## 步骤 4：第一个磁盘工具 + LangGraph Agent 循环（Phase 3）✅ 已完成

**目标**：模型从"只会聊天"变成"能真的干活"——第一次跑通 Agent 核心循环。

**改动内容**：

- `backend/requirements.txt`：新增 `langgraph`（含 langgraph-prebuilt）
- `backend/app/tools.py`（新增）：`@tool` 定义第一个工具 `scan_directory_size(path="")`
  - 安全设计：只读（只统计大小，不动文件）、白名单目录（用户主目录 / 系统临时目录）、扫描深度上限 5 层、20 秒超时
  - `path` 留空时默认扫描用户主目录（防止模型瞎猜路径，见下方调试故事）
- `backend/app/agent.py`（新增）：用 LangGraph 组装"模型 ↔ 工具"循环
  - `StateGraph`：`agent`（模型思考节点）+ `tools`（ToolNode 执行工具）两个节点
  - `tools_condition`：模型输出里有工具调用就去 tools，没有就结束
  - System Prompt 里**动态注入**本机真实的用户主目录路径
  - `llm` 客户端从 main.py 迁入这里（兑现已知问题清单里的解耦）
  - `MAX_STEPS = 12`（recursion_limit）防止失控死循环
- `backend/app/main.py`（改写）：`/api/chat` 改为运行 Agent
  - `agent.astream(stream_mode="messages")` 只流式输出"模型节点"的文本片段
  - 新增 `{"tool": "工具名"}` SSE 事件（模型调用工具时通知前端；前端暂不展示，Phase 6 做可视化）
- 前端：**零改动**（旧的流式解析会自动忽略未知的 tool 事件）

**学到的概念**：

- Tool Calling 的本质：模型只输出"调用意图"（工具名 + 参数 JSON），执行发生在工具层
- 工具的 docstring 和参数说明就是给模型的"使用说明书"，模型靠它决定何时用、怎么传参
- Agent 循环：agent → tools → agent → … 直到模型不再发起工具调用
- `ToolNode`、`tools_condition`、`recursion_limit`
- 动态上下文注入：模型不知道你的电脑长什么样，需要的"现场信息"由程序注入 Prompt

**调试故事（重要）**：第一次测试时模型自己"猜"路径 `C:\Users\Administrator`（因为训练数据里这个路径最常见），扫描失败。修复两处：
1. 工具 `path` 参数改为可选，留空默认扫描用户主目录
2. System Prompt 里注入真实路径 `C:\Users\ASUS`，并明确"不要自己编造路径"

→ 第二次测试：模型正确调用工具，基于真实数据回答（27.7 GB，AppData 占 23.4 GB），还输出了规范的表格和清理建议。**这就是 Agent 工程日常：模型足够聪明但不了解你的环境，工程上要帮它补环境信息。**

**验收结果**：✅

- 问"我的用户目录下哪个文件夹最占空间"→ SSE 流中出现 `tool: scan_directory_size` 事件 → 基于真实扫描结果输出带表格的分析（引用了真实目录名和大小）
- 直连 8000 和经 Vite 代理（5173）均正常

**目标**：从 1 个工具扩展到一组工具，让 Agent 按问题类型自动选择、甚至组合调用。

  - 新增 `find_large_files(directory, min_size_mb=100, limit=20)`：递归找出单个最大的文件（深度上限 8 层、20 秒超时、白名单校验）
  - 新增 `detect_junk_dirs()`：盘点 9 类常见垃圾位置（用户/Windows 临时目录、更新缓存、回收站、pip/npm 缓存、Chrome/Edge 缓存、Windows.old），按大小排序并标注风险等级；**路径写死、零外部输入**，无被诱导扫描危险目录的可能
  - 新增辅助函数 `_walk_files()`；新增常量 `MAX_FILE_DEPTH`
  - `TOOLS` 列表扩展为 3 个工具
- `backend/app/agent.py`（修改）：SYSTEM_PROMPT 的工具说明扩展为三个，并写明**选择原则**（"哪个文件夹占空间→scan_directory_size；哪个文件最大→find_large_files；有什么垃圾可清理→detect_junk_dirs；可组合使用"）
- 前端：零改动

**学到的概念**：

- 多工具场景下，模型靠 **description + 工具名 + Prompt 里的选择规则** 挑工具
- 工具描述写清"何时用我、何时用别人"，可以消除能力边界模糊带来的误选
- 同类安全工具的不同约束方式：任意路径工具用"白名单校验"，固定清单工具用"路径写死、不接受输入"

**验收结果**：✅（两轮真实测试）

## 步骤 6：清理建议 + 人工确认删除（Phase 5）✅ 已完成

**目标**：Agent 从"分析"进化到"能动手删"，同时建立安全底线——任何删除必须人工确认，且只进回收站。

**改动内容**：

- `backend/requirements.txt`：新增 `send2trash`（删除到回收站）
- `backend/app/tools.py`（扩展）：新增第 4 个工具 `delete_to_recycle_bin(paths)`
  - 安全三重校验：存在性、白名单范围、系统关键位置黑名单（Windows / Program Files / ProgramData / 根目录本身）
  - 一次最多 50 项；只删到回收站（可恢复），不做永久删除
  - **函数体内部调用 `interrupt(...)`：执行到这里整个 Agent 图暂停**，等用户决定；恢复后继续或放弃
- `backend/app/agent.py`（修改）：
  - 图编译时挂上 `InMemorySaver` checkpointer（interrupt 暂停/恢复的前提，状态按 thread_id 存取）
  - System Prompt 增加"删除纪律"：先扫描分析再删、只删用户点名的东西、禁删系统目录、用户拒绝立即停止
- `backend/app/main.py`（修改）：
  - 请求新增 `thread_id`（前端生成，Agent 状态按它存取）
  - 流结束后检测图是否停在 interrupt 上，若是则推送 `{"confirm": {...}}` SSE 事件
  - 新增 `POST /api/confirm`：用 `Command(resume=approved)` 恢复被暂停的图并继续流式输出
- 前端（新增 confirm 流程）：
  - `src/components/ConfirmCard.tsx`（新增）：黄色警示卡片，展示待删除清单 + "确认删除/取消"按钮
  - `src/api.ts`（改写）：抽出通用 `readSSE`，支持 `confirm` 事件；新增 `confirmAction()`
  - `src/App.tsx`（修改）：thread_id、待确认状态；确认期间输入框禁用；恢复后的回答继续流式上屏
  - `src/App.css`：确认卡片样式

**学到的概念**：

- **human-in-the-loop**：危险操作前暂停，由人做最终决定
- **LangGraph interrupt + checkpointer**：暂停时状态必须持久化到 checkpointer，恢复靠 `Command(resume=...)`
- 工具里调用 `interrupt()` 会让"工具执行"变成两段：确认前跑一半、确认后接着跑（工具会从头重跑，所以副作用必须放在 interrupt 之后）
- 信任边界落地：确认由服务端图状态驱动，前端只是个"按按钮的"，伪造前端请求骗不过服务端校验

**验收结果**：✅（两轮端到端测试，用临时目录里的真实文件）

1. **批准流程**：让 Agent 删除 `%TEMP%\cclear_test` 里的 3 个文件 → 它先扫描（scan_directory_size）→ 请求删除 → 收到 confirm 事件（3 个路径）→ 模拟用户批准 → 恢复执行 → 文件全部进回收站（目录清空，0 残留）
2. **拒绝流程**：对另一个文件点"取消" → 模型回复"已停止删除操作，没有删除任何文件"；文件验证仍然存在

## 步骤 7：过程可视化：工具时间线 + 心跳 + 粘连修复（Phase 6）✅ 已完成

**目标**：把后端已经推出来的"过程信息"变成界面上看得见的东西，并修掉两个体验欠账。

**改动内容**：

- `backend/app/main.py`：
  - **心跳**：等待模型输出的 `asyncio.wait` 超时后发送 `: ping` SSE 注释行（间隔可用环境变量 `HEARTBEAT_SECONDS` 覆盖，默认 10 秒）；关键细节：不能用 `wait_for`（超时会取消取片段的协程、弄断流）
  - **工具结果事件**：工具节点完成时推 `{"tool_result": {name, chars, preview}}`（前端时间线用）
  - **粘连修复**：检测到工具调用时额外推一个 `\n\n` 的 delta，把"调用前的自言自语"和"最终回答"分开
- 前端：
  - `components/ToolTimeline.tsx`（新增）：工具调用时间线芯片（"扫描目录占用 · 进行中… / · 完成（261 字符）"）
  - `api.ts`：解析 `tool` / `tool_result` 事件；忽略 `: ping` 注释行
  - `App.tsx`：`toolActivity` 状态，新对话清空；`App.css`：时间线样式

**学到的概念**：

- SSE 心跳：以 `:` 开头的行是协议规定的注释，前端天然忽略；作用是保活连接（防代理掐空闲连接）
- "等待+定时器"的正确写法：`asyncio.wait`（不取消任务）vs `asyncio.wait_for`（超时即取消，会把流打断）
- 过程可视化：Agent 产品"透明"理念的前端实现——用户知道 AI 正在干什么，而不是对着转圈干等

**验收结果**：✅

- 工具事件 + 工具结果事件均正常推送（`scan_directory_size` 261 字符、`detect_junk_dirs` 629 字符）
- 粘连修复生效：回答变为"我来扫描一下你的用户目录。\n\n# 用户目录占用排行…"（段落分开）
- 心跳验证：以 `HEARTBEAT_SECONDS=2` 启动，长扫描期间实测收到 1 次 ping；恢复默认 10 秒
- 前端 `npm run build` 通过

## 步骤 9：对话记忆 —— SQLite 持久化 + 服务端历史（Phase 7a）✅ 已完成

**目标**：把"对话历史"从前端搬到服务端，让 Agent 拥有真正的**记忆**：多轮上下文、刷新不丢、重启不丢。

**架构变化（重要）**：

- **之前**：历史存在前端，每次请求把全量历史发回后端（"无记忆服务"模式）
- **现在**：前端每轮只发**一条新消息**；历史全部由 checkpointer 按 `thread_id` 存在服务端（"有记忆服务"模式）——这正是主流 Agent 产品的做法（OpenAI Assistants 的 thread、Claude 的 conversation 都是这个模型）

**改动内容**：

- `backend/requirements.txt`：新增 `langgraph-checkpoint-sqlite`
- `backend/app/config.py`：新增 `CHECKPOINT_DB`（默认 `backend/data/cclear.db`，可环境变量覆盖；删文件 = 重置所有对话）
- `backend/app/agent.py`：
  - `InMemorySaver` → **`AsyncSqliteSaver`**（踩坑记录：同步版 `SqliteSaver` 与 `astream` 的异步接口不兼容，会报 "does not support async methods"；异步 checkpointer 还要求图在**应用启动时**初始化——因为需要运行中的事件循环，所以改为 FastAPI lifespan 里调 `init_agent()`）
  - 增加 `init_agent() / close_agent()`：打开/关闭数据库连接
- `backend/app/main.py`：
  - **协议变更**：`ChatRequest` 从 `{messages: [...]}` 改为 `{thread_id, message}`（只发新消息）
  - 新增 `GET /api/history?thread_id=...`：从 checkpointer 读状态，转成前端可渲染的消息列表（过滤 ToolMessage；连续 AI 消息合并）
  - `get_state` → `aget_state`（异步 checkpointer 配套）
  - history 响应携带 `pending_confirm`：刷新时如果正停在删除确认，卡片能恢复
- 前端：
  - `api.ts`：`streamMessage(threadId, message)`；新增 `fetchHistory()`
  - `App.tsx`：`thread_id` 存入 **localStorage**（刷新还是同一个对话）；打开页面自动恢复历史；新增"**新对话**"按钮（换新 thread_id）
  - `App.css`：顶栏按钮样式

**学到的概念**：

- **Agent 记忆的分层**（**注意"短期"和"会话"不是同一层，前者不落盘、后者落盘**）：

  | 层级 | 是什么 | 生命周期 | 存在哪 |
  | --- | --- | --- | --- |
  | **短期记忆** | 本次请求真正发给模型的 `messages` 列表（含压缩后的视图） | **一次请求内**，请求结束即消失 | **不存**，进程内存 |
  | **会话记忆** | 按 `thread_id` 存档的完整历史（每条 user/ai/tool 消息 + 每一步状态） | 跨请求、跨刷新、跨重启 | `data/cclear.db` 的 `checkpoints` / `writes` 表 |
  | **长期记忆** | 跨会话的用户偏好（"500MB 以上才提醒我"） | 永久（除非手动删） | `data/profile.db` 的 `preferences` 表 |

  **关键理解**：短期记忆**不是独立存储**，而是"每次从会话记忆里读出来、压缩后拼给模型的临时副本"。
  即：`checkpoints` 表 ──读出全部历史──► `compact_messages()` 压成视图 ──► 本次请求的短期记忆。
  所以"短期记忆存的不也是会话吗"——**数据来源是会话，但短期记忆本身从不落盘**。
- checkpointer 的三重身份：interrupt 暂停恢复、对话记忆、时间旅行——**同一个机制，三种用途**
- 同步/异步接口配套问题：`astream` 必须配异步 checkpointer；异步组件需要在事件循环里初始化（lifespan）
- 状态归属原则："唯一事实来源"在服务端，前端只是视图

**验收结果**：✅（三轮测试）

1. **同线程记忆**：先说"我最喜欢的颜色是蓝色"→ 再问"我最喜欢什么颜色？"→ 正确回答"蓝色"（旧架构下也可以，但全靠前端重发历史；现在靠服务端）
2. **历史接口**：`GET /api/history` 返回 4 条干净消息（user/assistant 成对，工具消息被过滤）
3. **持久化**：**重启后端**后再查历史，4 条消息仍在（SQLite 存档生效）
4. **回归**：新的单消息协议下，删除确认流程（interrupt/resume）依旧工作正常，文件成功入回收站
5. **补丁**：刷新后图表丢失的问题——`/api/history` 现在同时返回历史中所有工具产出的 `artifacts`（从 ToolMessage 提取），前端用它重建图表卡片；前端映射逻辑抽成 `artifactToCard()` 供"实时流"与"历史恢复"共用

## 步骤 16：用户画像（长期记忆）✅ 已完成

**目标**：让 Agent **跨会话**记住"这个人是什么样"——你说过一次"500MB 以上才提醒我"，开新对话也不用重说。

**第一步是把概念分清（这是本步最重要的认知）**：

| | 存什么 | 按什么索引 | 换会话还在吗 | 存储 |
| --- | --- | --- | --- | --- |
| **对话记忆**（已有） | 这次聊了什么 | `thread_id` | ❌ 不在 | `data/cclear.db` |
| **用户画像**（本步） | 这个人什么样（偏好） | `user_id` | ✅ 在 | `data/profile.db` |

一句话：**checkpointer 是"你上次说了什么"，画像是"你是个什么人"**。

**新增文件**：

- `backend/app/profile.py`：画像存储。SQLite 一张 key-value 表（`user_id, key, value, updated_at`）+ **进程内缓存**
  - `init()` 建表并加载缓存；`set_preference()` / `forget_preference()` / `get_all()` / `snapshot()`
  - `prompt_section()`：把画像渲染成注入 System Prompt 的一段文字（空画像返回空串，绝不塞空标题浪费 token）
  - 保护上限：最多 50 条、key ≤ 48 字符、value ≤ 400 字符——**画像每轮都进 Prompt，必须防止无节制膨胀**
- `backend/tests/test_profile.py`：11 个测试（增删改查、覆盖、上限、空画像不注入、**重启后仍在**、**System Prompt 确实带上了画像**）
- `frontend/src/components/ProfilePanel.tsx`：侧栏"AI 记住的偏好"卡片，**每条都能手动删除**（记忆必须可见、可撤回）

**修改**：

- `backend/app/config.py`：新增 `PROFILE_DB`、`PROFILE_USER_ID`（默认 `local`，多用户时从认证取）
- `backend/app/tools.py`：新增 `remember_preference(key, value)` / `forget_preference(key)` 两个工具（同步函数，做 SQLite 小 IO，够快不必异步）
- `backend/app/agent.py`：`SYSTEM_PROMPT` 拆成常量 + `build_system_prompt()`——**每次调用现拼**（画像随时会变，启动时拼接会导致"刚记住的偏好这轮不生效"）；`init_agent` 先 `profile.init()`
- `backend/app/main.py`：`GET /api/profile`（**不需要 thread_id**，因为它跨会话）、`DELETE /api/profile/{key}`
- `frontend/src/api.ts` + `App.tsx` + `App.css`：新增画像类型与接口；`remember/forget` 跑完后侧栏自动刷新（`profileVersion` 计数器触发重新拉取）

**关键设计决策**：

1. **为什么用 key-value，不用向量库**：偏好是结构化事实（阈值、禁区、习惯），精确命中、可读、**人能直接改**；向量检索适合"语义模糊召回"，那是另一个问题——**别为了高级而高级**
2. **为什么加内存缓存**：每轮对话都要拼 Prompt，每次都查库等于把本地 IO 放进最热路径；画像是几十条的小数据，缓存在内存成本为零，**写入时同步更新缓存**，读永远最新
3. **为什么画像单独一个库**：生命周期不同。对话存档可以随会话删；画像是长期资产，不应该被"清空对话"牵连
4. **为什么让模型自己决定记什么**：`remember_preference` 的 docstring 里明确写"该记 vs 不该记"和"不记隐私信息"——**把判断标准写在工具说明书里，比在代码里硬编码规则更灵活**
5. **为什么侧栏要能删**：记忆不透明 = 不可控。用户必须能看到、能撤回，否则"它怎么知道这个"会变成信任问题

**实际踩的保护点**：`get_all()` 在 `profile.init()` 未调用时原本返回空列表，导致 API 在无 Key 时也"看起来正常但没数据"——改成 `_connect()` 里做懒初始化兜底（`if _db_path is None: init(PROFILE_DB)`），才不会出现"忘了 init 就静默失效"。

**验收结果**：✅

- `47 passed`（新增 11 个画像测试 + 2 个 API 契约测试）
- 前端 `tsc --noEmit` 通过；`npm run build` 通过（首屏仍 120.7 KB gzip）
- **真实端到端（三次独立会话）**：
  - 会话 A："记住以后 500MB 以上才提醒我" → 调用 `remember_preference`，写入 `{大文件阈值: 500MB 以上的文件才需要提醒我}`
  - **会话 B（全新 thread_id）**：问"我的大文件阈值是多少" → 答 **"你的大文件阈值是 500MB"** ← 跨会话记忆成立
  - 会话 C："忘掉大文件阈值" → 调用 `forget_preference`，画像清空
- `/api/profile` 空画像返回 `{"user_id":"local","entries":[]}`；`DELETE` 不存在的 key 返回说明而非 500

## 步骤 17：记忆压缩 ✅ 已完成

**目标**：长对话不撑爆上下文，又不丢关键信息。

**先测量，再动手**（这一步的产出比代码更值钱）：

```
=== 现有存档的真实构成（89 快照 / 16 会话）===
human  条数=21  平均= 25 字符
ai     条数=34  平均=191 字符  最大=874
tool   条数=15  平均=205 字符  最大=632
最大会话：11 条消息 / 2748 字符 ≈ 900 tokens

=== 工具输出的"理论最坏值"（真实 C 盘实测）===
find_large_files(min=50MB, limit=20)    → 2,322 字符
find_large_files(min=50MB, limit=50)    → 4,988 字符
find_large_files(min=50MB, limit=100)   → 10,426 字符  ← 单条就 1 万字符！

单行样本（Windows 路径极长）：
[162 字符] - 784.1 MB  C:\Users\ASUS\AppData\Local\Packages\B9ECED6F.ArmouryCrate_...\DRV_VGA_Intel_RPL_SZ_W11_64_...zip
```

**结论**：
1. **日常对话根本不是瓶颈**（十几轮才 900 tokens），所以"按轮次摘要"是过度设计
2. **真正的风险是单条工具输出**（模型把 `limit` 提到 100 就是 1 万字符）
3. 所以要做的是**两层**，而不是一味压缩对话历史

**新增文件**：

- `backend/app/compact.py`：压缩逻辑（纯函数，不碰数据库）
  - `compact_messages(messages) -> (新消息列表, CompactStats)`：核心
  - `validate_tool_pairs(messages) -> list[str]`：**配对体检**（压缩后必过）
  - `CompactStats.as_dict()`：压缩前后对比，供接口/日志展示
- `backend/tests/test_compact.py`：16 个测试（含"按行截断绝不切半行""最后一轮不可动""配对永不断裂"等硬约束）

**修改**：

- `backend/app/config.py`：新增 `COMPACT_KEEP_TURNS`（默认 4）、`COMPACT_MAX_TOOL_CHARS`（默认 1500）、`COMPACT_ENABLED`（开关，便于对比）
- `backend/app/agent.py`：`call_model` 里先压缩再发模型；`build_system_prompt(compact_note)` 接收"已省略"说明
- `backend/app/main.py`：新增 `GET /api/context/{thread_id}`——只读体检接口，回答"为什么它忘了前面说的"

**两层压缩策略**：

| 层 | 处理对象 | 做法 |
| --- | --- | --- |
| ① **旧轮次剪枝** | 最近 4 轮之外的历史 | 只留"用户问题 + 最终结论"，**整段丢弃**工具调用和原始输出 |
| ② **工具输出限长** | 历史轮次的工具结果 | 超 1500 字符截断 + 注明"已截断" |
| ③ **最后一轮不碰** | 当前正在进行的这一轮 | **原封不动**——模型正靠它干活 |

**核心设计决策**：

1. **压缩只影响"发给模型的视图"，绝不改存档**
   存档要同时服务三件事：`/api/history`（用户看完整记录）、`interrupt/resume`（恢复现场）、可追溯（查模型到底看到了什么）。改小了这三件全毁。所以：**存档是完整真相，视图是压缩副本**。
2. **为什么丢工具输出而不丢对话**：AI 的**最终回答本身就是对工具数据的提炼**（"AppData 占 23.6GB"就是从一堆清单里总结出来的），原始清单已经冗余。而对话是"用户说过什么"，丢了就真忘了。
3. **必须守住的不变量：`AIMessage(tool_calls)` 与 `ToolMessage` 必须成对**
   - 只留 ToolMessage 不留调用 → API 直接 400
   - 只留调用不留 ToolMessage → API 直接 400
   所以剪枝只能**整段丢弃**，且截断时用 `model_copy` 保住 `tool_call_id`。`validate_tool_pairs()` 就是这条不变量的体检器——**宁可测试失败，也不要线上 400**。
4. **不往 messages 里插 SystemMessage**：多数 API 只允许 system 角色在开头。改成把"已省略 N 轮"的说明交给 `build_system_prompt` 拼进真正的 System Prompt。

**实测踩到的坑**：

- 第一版把"已省略"说明做成 `SystemMessage` 插在消息中间 → 结构上有风险（OpenAI 兼容接口对 system 位置敏感）。改为拼进开头 System Prompt
- 第一版把**最后一轮**也截断了 → 模型拿不到当前工具结果，回答质量会崩。修正为"最后一轮原样保留"

**端到端验收（同一会话连跑 6 轮）**：

```
第 1 轮  扫描目录 → 410.2 KB，最大 file_6.bin
第 2 轮  复扫确认 → 一致
第 3 轮  "第二个大的呢" → file_5.bin 97.7 KB（记忆连贯，未压缩）
第 4 轮  "刚才第一个问的是什么" → 准确复述（未压缩）
第 5 轮  [compact] 15→12 条消息，3236→2584 字符，丢弃 1 轮  ← 压缩开始生效
         "总结这个目录" → 仍准确
第 6 轮  [compact] 17→11 条消息，3921→2203 字符，丢弃 2 轮，省 44%
         "我一共问了你几个问题" → 仍答出全部问题

=== 存档状态 ===
消息数=18  字符=3415   ← 存档完整，压缩只影响视图
```

**测试结果**：`63 passed`（新增 16 个压缩测试）

**后续修正：把"按字符截断"改成"按行截断"**

第一版用的是 `content[:1500]`（纯字符切片），实测发现会切出半截路径：

```
旧： ...\Programs\Ollam|…（已截断）        ← "Ollama" 被切成 "Ollam"
新： ...\OpenAI\Codex\bin\...\codex.exe
     …（输出过长，后面还有 87 行未显示）   ← 整行完整，且告知剩多少行
```

**为什么必须按行**：工具输出是"一行一个文件"的清单，半截路径会让模型误判或复述错。
**退化处理**：若第一行本身就超限（如压成单行的 JSON），只能按字符切，但明确标注"单行过长"。

**学到的概念**：

- **先测量再优化**：直觉说"对话历史太长"，数据说"单条工具输出才是炸弹"——**优化前先量化，否则就是凭感觉写代码**
- **存档 vs 视图分离**：真相只存一份且不改，展示/传输层按需投影（和数据库"视图"同一个思想）
- **压缩的合法性边界**：压缩必须保持"结构不变量"（tool_calls 配对），否则省了 token 换来 400
- **LLM 输出天然是摘要**：AI 最终回答已经是对工具数据的提炼，所以丢原始输出几乎无损——**利用已有信息，别重复造摘要**
- **越"当前"的数据越不能动**：最后一轮是模型正在作业的现场，压缩它等于让人闭眼干活

## 步骤 18：扫描进度提示（等待可视化）✅ 已完成

**问题**：扫描用户主目录实测要 **10 秒**（SSE 实测：`tool` 事件 1.2s → `tool_result` 11.1s），期间前端只有三个跳动的点，用户无法判断"在扫"还是"卡死"。

**方案选择**（三选一，取最便宜的）：

| 方案 | 做法 | 成本 | 结论 |
| --- | --- | --- | --- |
| **A. 计时器 + 阶段文案** | 纯前端，显示"扫描目录占用中… 12s" | 5 分钟 | ✅ **选它** |
| B. 轮询进度接口 | 工具写进度，前端每 500ms 拉一次 | 2 小时 | ❌ 已有 SSE，不该降级成轮询 |
| C. LangGraph `custom` 流 | 工具内 `get_stream_writer()` 推真实进度 | 半天 | 留作后续（真正能学到东西的版本） |

**实现**：

- `TypingIndicator` 新增 `startedAt` + `runningTool` 两个 prop：前者算已等待秒数，后者显示当前在做什么
- 文案随等待时长递进：`思考中` → `扫描目录占用中…` → `扫描目录占用中，大目录会比较慢…` → `正在整理结果…`
- 3 秒后才显示秒数（避免一闪而过的数字干扰）
- 新建 `frontend/src/toolLabels.ts`：工具名 → 中文短语，时间线与等待提示共用一份

**踩到的三个坑（值得记）**：

1. **`content === ''` 判断会失效**：后端在"调用工具"时会先推 `{"delta": "\n\n"}` 把自语和最终回答分开，`content` 因此变成 `"\n\n"`——严格相等判断会让提示在最需要它的扫描阶段消失。改成 `content.trim() === ''`
2. **模型会"先说再扫"**：实测它先流式输出"我先扫描一下你的用户主目录…"，然后才调工具。此时占位气泡已被正文替换，所以要**额外一行**提示（用 `hasVisibleAnswer` 区分，避免与占位气泡重复）
3. **lint 禁止 effect 里同步 setState**：初版在 `useEffect` 里 `setElapsed`，触发 `react(set-state-in-effect)` 警告。改成只存 `now`，已等待时长在渲染时算出来

**验证**：`tsc -b` 无错、`oxlint` 无警告、SSE 实测确认 `tool` 事件先于 10 秒扫描到达

**学到的概念**：

- **长任务的焦虑来自"无信息"，不是"慢"**：给个秒数就能把"是不是卡死了"变成"它在动"
- **进度提示的成本可以极低**：不需要真实进度，只需要"可证伪的时间流逝"
- **阶段文案 > 百分比**：没有真实百分比时，编一个假的 37% 比不写更糟——**只说确定的（在扫什么），不说不确定的（还有多久）**

## 步骤 19：版本控制与 CI ✅ 已完成

**做了什么**：

- `git init` + 首次提交（61 个文件），此后每次改动可回退、可对比
- `.gitignore` 守住三类不该入库的东西：`.env`（API Key）、`backend/data/*.db`（真实对话）、`.venv`/`node_modules`（依赖）
- `.gitattributes` 统一换行符（`* text=auto eol=lf`，`.ps1` 保留 CRLF）
- `.github/workflows/ci.yml`：push / PR 时自动跑 **后端 pytest** + **前端 tsc + oxlint**
- 推到 `github.com/OneforMe98/cclear`，**首次 CI 全绿，耗时 64 秒**

**为什么 CI 用 `windows-latest` 而不是 `ubuntu-latest`**：

本项目删除文件走 Windows 回收站（`send2trash`）、路径是 `C:\Users\...`、安全白名单按 Windows 目录写。在 Linux 上跑测试**测不到真实行为**，等于自欺欺人。代价是机器启动慢约 1 分钟，但值得。

**踩到的坑**：

1. **在错误的目录 `git init`**：第一次 shell 工作目录残留在 `backend/`，仓库建在了 `backend/.git`，导致 `frontend/`、`docs/` 完全不在版本控制里。用 `git rev-parse --show-toplevel` 才发现，删掉重建
2. **`github.com:443` 被网络阻断**（`api.github.com` 正常、`github.com:22` 通），必须开代理才能 push。这也解释了为什么"有些网站能上、GitHub 打不开"
3. **GCM 的 TLS 校验被关闭**：push 时出现 `TLS certificate verification has been disabled` 警告——这是本机 Git Credential Manager 的既有配置，不属于本项目，但值得留意（见"已知问题"）

**学到的概念**：

- **pytest 是工具，CI 是机制**：pytest 负责"怎么测"，CI 负责"谁在什么时候自动测"
- **GitHub Actions 不是"GitHub 变成服务器"**：你在 yml 里声明 `runs-on: windows-latest`，GitHub 从自己的虚拟机池临时分配一台，跑完即销毁。公共仓库免费且不限时长
- **CI 的价值不在"多跑一次测试"，而在"忘不掉"**：本地靠自觉，CI 靠强制

## 步骤 20：LangSmith 链路追踪（可选，默认关闭）✅ 已完成

**目的**：不靠 `print` 猜，直接在网页上看清每次 Agent 运行的全过程。

```
一次对话的 trace（在 smith.langchain.com 上看）：
├── call_model        1.2s   token 1240 in / 86 out
├── tools            10.3s
│   └── scan_directory_size
├── call_model        1.8s   token 1580 in / 420 out
└── 总计             13.3s   token 2820
```

**⚠️ 隐私是这条的第一原则**

上报内容包含**完整对话文本 + 工具原始输出**——也就是"你问了什么"和"扫到了哪些文件路径"。这是把本机信息传到云端，所以设计上做了三重保护：

| 保护 | 实现 |
| --- | --- |
| **默认关闭** | `LANGSMITH_TRACING` 缺省即关，不配永远不会上报 |
| **必须两项齐备** | 只有开关注入、没有 Key → 不启用；只有 Key、没有开关 → 也不启用 |
| **显式写回 false** | 未启用时主动把 `LANGSMITH_TRACING=false` 写回环境，防止"上次开过忘了关" |
| **启动时大声提示** | 启用后后端控制台打印 `[langsmith] 已启用链路追踪 → 项目 cclear（对话内容将上报云端）` |

**改动**：

- `backend/app/config.py`：新增 `LANGSMITH_TRACING` / `LANGSMITH_API_KEY` / `LANGSMITH_PROJECT` / `LANGSMITH_ENABLED`
  - 关键点：LangChain 读的是 **`os.environ`**，不是 Python 变量，所以启用时必须把值**写回环境变量**
  - 同时写新旧两套变量名（`LANGSMITH_*` 与 `LANGCHAIN_*`），兼容不同版本 SDK
- `backend/app/agent.py`：`init_agent` 里打印启用提示
- `backend/app/main.py`：`/api/health` 增加 `langsmith` 字段，一眼看出当前是否在上报
- `backend/.env.example`：补上配置说明与隐私提醒
- `backend/tests/test_config.py`：新增 3 个测试（默认关闭、半配不生效、关闭时清变量）

**验证**：

```
默认（不配任何东西）  → LANGSMITH_ENABLED = False
                        os.environ['LANGCHAIN_TRACING_V2'] = 'false'
只配开关不配 Key      → False
只配 Key 不配开关     → False
两者齐备              → True，且环境变量已写回 'true'
```

**怎么开启（需要你自己做）**：

1. 注册 https://smith.langchain.com
2. Settings → API Keys → 创建，复制 `lsv2_pt_...`
3. 在 `backend/.env` 里加三行：

```ini
LANGSMITH_TRACING=1
LANGSMITH_API_KEY=lsv2_pt_你的密钥
LANGSMITH_PROJECT=cclear
```

4. 重启后端，控制台出现 `[langsmith] 已启用链路追踪`
5. 聊两句，去网页看 trace

**学到的概念**：

- **可观测性（Observability）**：日志只告诉你"出错了"，trace 告诉你"慢在哪一步、花了多少 token、模型到底收到了什么"
- **配置读的是环境变量而非 Python 变量**：第三方库通常直接读 `os.environ`，改了 `config.XXX` 它不认——这类"隐形契约"是集成时的常见坑
- **隐私开关必须"默认为关 + 半配不生效 + 启动大声提示"**：只要有一条缺失，用户就会在不知情的情况下把数据传出去

## 已知问题与待升级清单

> 开发中发现但按计划延后处理的问题，记录在此，后续阶段逐个升级。

| 问题 | 风险 | 计划处理 |
| --- | --- | --- |
| SYSTEM_PROMPT 写死在代码里 | 改话术要改代码 | 后期挪到配置/数据库/后台管理 |
| SQLite 存档的单连接下，**同一 thread 并发**仍可能锁竞争 | 实测不同 thread 并发正常；同一 thread 同时两次请求才可能冲突 | 前端已用 `loading` 挡重复发送，风险很低；生产化换 Postgres/Redis checkpointer |
| 删除上限 50 按"条目"计，不按体积/文件数 | 传一个大目录（内含数千文件）只算 1 项；缺少体积阈值提醒 | 未来加"单次删除体积阈值提示"与分批确认 |
| Windows 下 uvicorn 热重载偶发漏检 | 小概率改了代码没生效 | 改完看终端是否出现 Reloading，必要时手动重启 |
| SSE 无前端自动重连（服务端心跳已就绪） | 网络抖动时会话中断，只能手动重发 | 前端自动重连/断点续传（需服务端快照配合） |
| 模型在"打招呼"类问题里也会先调工具扫描 | 多花一次扫描时间和 token，体验略差 | 可优化 System Prompt 的工具使用门槛（小改动） |
| 画像目前是"模型自己判断该记什么" | 可能记多/记少；用户需在侧栏确认 | 侧栏已可见可删；后续可加"记住前先确认"开关 |
| ~~本机 Git Credential Manager 关闭了 TLS 校验~~ | ~~凭据传输理论上可被中间人截获~~ | ✅ **已修复**：`git config --global http.sslVerify true`（原为 `false`）；并已改用 SSH 推送，不再依赖 HTTPS 凭据传输 |
| 画像无版本/历史（只存最新值） | 覆盖后看不到旧值 | 当前够用；若要做"偏好变更历史"再加表 |
