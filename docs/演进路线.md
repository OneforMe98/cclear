# CCLEAR 演进路线（Roadmap）

> 本文档回答一个问题：**CCLEAR 现在能做什么、接下来值得做什么、为什么按这个顺序做。**
> 与 [开发进度.md](开发进度.md)（记录"已经做了什么"）互补——本文关注"未来"。

---

## 0. 当前所处位置

CCLEAR 已完成一个**完整闭环的本地 Agent 产品**（Phase 0–7）：

```
自然语言提问 → 工具扫描 → 结构化分析 → 图表可视化 → 人工确认 → 回收站删除
                                  ↑
                        对话记忆 / 暂停恢复 / 自动化测试守护
```

**定位很重要**：这是一个**操作本机文件系统**的工具。因此它的"演进"不是"往云上堆规模"，而是沿着两条线走：

- **能力线**：让它变得更聪明、更安全、更懂你（Agent 能力）
- **工程线**：让它更易维护、更可测试、更接近生产标准（工程质量）

---

## 1. 演进原则（先立规矩，再谈功能）

| 原则 | 含义 |
| --- | --- |
| 安全优先于能力 | 任何新能力都不能削弱"删除必须人工确认 + 可恢复"这条底线 |
| 先评估再实现 | 每个候选项先判断**是否适合本项目**（✅/⚠️/❌/🔬），不适合的明确写"不做"及原因——**评估能力比实现能力更值钱** |
| 先记录后实现 | 新想法先进本路线图，评估优先级再做，不做"拍脑袋加功能" |
| 每步可讲明白 | 承接项目初心——每一步都要能对着代码讲清楚 |
| 本地优先 | 涉及文件操作的能力，永远在本机执行，数据不出域 |

## 2. 演进分层：按"值得做的优先级"排列

### 🟢 第一梯队：低风险、高回报（✅ 已于步骤 14 全部完成）

| 能力 | 为什么值得做 | 涉及改动 | 学到什么 | 状态 |
| --- | --- | --- | --- | --- |
| **错误兜底文案** | 步数超限时把原始异常丢给用户，体验差 | `user_facing_error()`：异常→人话；详细原因进日志 | 异常分层、用户文案 vs 开发日志 | ✅ 完成 |
| **温度/参数入配置** | `temperature` 等写死在 `agent.py` | `MODEL_TEMPERATURE` / `AGENT_MAX_STEPS` 进 `config.py` | 配置外置、单一来源 | ✅ 完成 |
| **前端代码分割** | recharts 让首屏 ~225KB gzip | `React.lazy` + `Suspense` 懒加载图表 | 按需加载；首屏降到 120KB | ✅ 完成 |
| **消息时间戳** | 未来做"历史列表/会话管理"需要 | 后端从状态快照取时间 → 前端显示 HH:MM | 数据契约演进、快照方向陷阱 | ✅ 完成 |

### 🟡 第二梯队：Agent 能力的"真升级"

| 能力 | 为什么值得做 | 涉及改动 | 学到什么 | 适合度评估 |
| --- | --- | --- | --- | --- |
| **MCP 化工具** | 工具与 Agent 解耦的行业标准；可被 Cursor/Claude Desktop 复用 | 独立 MCP Server + `langchain-mcp-adapters` Client | MCP 协议、进程间工具调用、解耦 | ❌ **不适合（已实验并回滚）**：只一个本地调用方，解耦零收益；净增进程/编码/孤儿进程成本；唯一收益"能被 Cursor 复用"不足以支撑维护 |
| **长期记忆（用户画像）** | 跨会话记住"这个用户怕删浏览器缓存" | 偏好存 SQLite；注入 System Prompt 或按需检索 | 记忆分层、画像 vs 语义记忆 | ✅ **已完成（步骤 16）**：key-value 存 SQLite + 每轮注入 System Prompt + 侧栏可见可删 |
| **记忆压缩** | 长对话撑爆上下文窗口、token 变贵 | 历史超阈值时"最近 N 条 + 早期摘要" | 上下文管理、摘要、成本控制 | ✅ **已完成（步骤 17）**：**测量后发现原方案不对症**——对话轮次很少（十几轮才 900 tokens），真正的大头是单条工具输出（limit=100 时实测 1 万字符）。最终做成两层：旧轮次剪枝 + 工具输出限长，且只压缩"发给模型的视图"、存档不动 |
| **多轮规划** | 复杂任务（"帮我清出 10GB"）需要先规划再执行 | 加规划节点 / 子任务拆分；预算控制 | Planning、任务分解、预算 | ❌ **不适合**：本项目任务本质是"扫描 → 分析 → 确认删除"，1–3 步就能完成，模型自己就能组合工具。加规划节点是**过度设计**，还会拖慢响应 |
| **手写 mini ReAct loop** | 理解 LangGraph 底层在做什么 | 独立 40 行循环脚本，不动主流程 | Agent 引擎本质、摆脱黑盒 | ❌ **已评估不做**：核心知识（图 = while 循环 + 存档 + 暂停）已在步骤 17 的讨论中讲透，等价代码仅 20 行、已作为笔记归档。**判断：想懂引擎不必再造一个引擎**，直接读 `tools_condition` 源码（15 行）比手写更快 |

### 🔴 第三梯队：生产化 / 多用户（架构级改造）

| 能力 | 为什么现在不做 | 涉及改动 | 学到什么 | 适合度评估 |
| --- | --- | --- | --- | --- |
| **多用户模型** | 当前是单机自用；多用户=重新设计信任/隔离模型 | `(user_id, thread_id)` 联合主键；认证；租户根目录 | 多租户、认证授权、隔离 | ❌ **不适合（与定位冲突）**：产品本质是"操作我自己的 C 盘"，多用户要先解决"每个人的 C 盘怎么隔离"——那就变成"本地代理 + 云端面板"了，是另一个产品 |
| **服务端存储升级**（Postgres/Redis） | SQLite 单连接有并发锁风险 | 换 checkpointer | 连接池、并发、分布式状态 | ❌ **不适合**：单用户场景 SQLite 完全够；为低频并发引入数据库服务不划算。**替代方案已天然满足**：实测 `cclear.db` 与 `profile.db` 均为 `journal_mode=wal` + `busy_timeout=5000`（LangGraph 的 `SqliteSaver.setup()` 自带 `PRAGMA journal_mode=WAL`，`aiosqlite` 默认 5s 超时），**无需额外配置** |
| **SSE 自动重连** | 需要服务端快照配合 + 断点续传语义 | 前端断线重连 + 后端可恢复流 | 长连接健壮性、断点续传 | ⚠️ **有条件适合（低优先）**：本地网络断线概率低，而扫描动辄 20 秒——真要改进，"扫描进度推送"比"断线重连"更值。断点续传成本很高 |
| **LangSmith 集成** | 需联网+注册；本地自用暂不必 | 配 `LANGCHAIN_API_KEY` 上报 trace | 可观测性、链路追踪、评测 | 🔬 **仅学习（性价比高）**：几行配置就能看到完整 Agent trace，**理解"一次请求花了多少 token、走了哪些节点"**很有教学价值；但别把它当产品功能 |
| **本地代理 + 云端面板** | 想"远程清扫自己电脑"才需要 | 云控前端 + 本机 Agent 代理 + 加密信道 | 分布式架构、远程执行模型 | ❌ **不适合（另一个产品）**：这是"远程运维"赛道，需要身份认证、端到端加密、穿透、多机管理——与"本地透明清理工具"是两条路 |
| **部署工程化** | 本机工具，Docker/Linux 容器与目的冲突 | CI（push 跑 pytest）、打包发行版 | CI/CD、发行工程 | ⚠️ **拆开看**：**CI 跑 pytest ✅ 适合**（几乎零成本，防回归，GitHub Actions 10 行）；**Docker/Linux 部署 ❌ 不适合**（容器看不到宿主 C 盘，与产品目的相悖） |

## 3. 为什么是这个顺序？（依赖关系 + 适合度过滤）

**先过滤，再排序**：不适合的项（❌）直接划掉，剩下才谈顺序。

```
🟢 第一梯队：已全部完成（清体验欠账）

─────────── 已落地（第二梯队）───────────
✅ 用户画像：跨会话长期偏好 · 步骤 16
✅ 记忆压缩：旧轮次剪枝 + 工具输出限长 · 步骤 17

─────────── 还能做，按价值排序 ───────────
⚠️ CI 跑 pytest                  ← 零成本防回归（前置：项目还没 git init）
🔬 LangSmith（只看 trace）        ← 几行配置，教学价值高
⚠️ 扫描进度推送                  ← 扫描 20 秒无反馈，UX 缺口

─────────── 明确不做（❌）───────────
MCP 化 · 多轮规划 · 手写 mini ReAct loop · 多用户 · Postgres/Redis · 本地代理+云端面板 · Docker 部署 · SSE 断线重连
```

**一句话逻辑**：**先判断"该不该做"，再排"先做哪个"**——评估能力比实现能力更值钱。

## 4. 如果只挑一件事做到极致（面试导向）

**推荐：CI 跑 pytest + 扫描进度推送**（按投入产出排序）。

理由：
1. **CI 是最便宜的防回归**：已有 63 个测试，但全靠手动跑；接上 GitHub Actions 后每次 push 自动验证，10 行 YAML
2. **扫描进度是真实的体验缺口**：`scan_directory_size` 最长 20 秒、期间前端只有"思考中"，用户不知道卡住还是没卡住
3. **两者都在"确定性"上投资**：一个防代码回归，一个防体验回归

**已排除的首选：手写 mini ReAct loop**
> 曾被评为"面试价值最高"，但评估后不做：**想懂引擎不必再造一个引擎**。核心结论（图 = while 循环 + 存档 + 暂停）已用 20 行等价代码讲透并归档；真要深入，直接读 `tools_condition` 源码（15 行）比手写 40 行脚本更高效。

**面试话术（两个"不做"的评估视角）**：
> "MCP 我试过并回滚了：只有一个本地调用方，解耦零收益，反而增加进程管理和编码约定成本。
> 手写 ReAct loop 我也评估过——本来被评为'面试价值最高'，但我判断**理解引擎不需要再造一个引擎**：读 15 行源码就能得到的结论，不值得花半天重写。
> **能写出来是技能，判断不该写是判断力。**"

## 5. 明确"不做"的事（边界也是设计）

| 不做 | 原因 |
| --- | --- |
| 把扫描逻辑搬到云服务器 | 与"操作本机文件"的产品本质冲突 |
| 无确认的一键删除 | 违背"透明可控"核心价值 |
| 追求 100% 测试覆盖率 | 测试预算应花在"确定性 + 高代价"的安全边界 |
| 为炫技堆砌框架（MCP、多轮规划等） | 项目初心是"每步都能讲明白"；无调用方的解耦是纯负担 |
| 把本地工具塞进 Docker | 容器看不到宿主 `C:\`，`send2trash` 也只会操作容器内回收站 |
